# Telegram Bot 接入

asms2 的 Telegram Bot 是**附加通道**，不改变邮件主链路：

- 站点 → Telegram：新邮件实时推送（含验证码提取）。
- Telegram → 站点：创建/查看临时邮箱、查看正文、标记已读、删除临时邮箱。
- **不支持在 Telegram 里发信**；发信仍走网页或 `/api/v1/send`。
- 推送是 best-effort：失败只写 `telegram_bot.last_error`，不影响邮件入库。

## 1. 前置条件

| 项        | 要求                                                                      |
| --------- | ------------------------------------------------------------------------- |
| 公网地址  | 必须是 **HTTPS**（Telegram 不接受 http 回调，localhost 也不行）           |
| 站点地址  | 管理后台「站点信息 → siteUrl」填对外地址，例如 `https://mail.example.com` |
| Bot Token | 在 Telegram 找 [@BotFather](https://t.me/BotFather)，`/newbot` 创建后获得 |

不需要新增环境变量：Token 与 Webhook Secret 都存在数据库里（AES-256-GCM 加密，只回显末四位），改完即时生效，不用重启。

## 2. 后台配置（管理员）

1. 打开 `/admin/telegram`。
2. 填 **Bot Token**，保存配置。保存时会调用 `getMe` 校验 Token，并记录机器人用户名。
3. 打开「启用 Telegram 机器人」，再次保存。
4. 点「注册 / 更新」，站点会调用 `setWebhook`，把
   `https://<siteUrl>/api/telegram/webhook` 注册给 Telegram，并带上 `secret_token`。
5. 页面显示「已注册」地址与注册时间即成功。
6. 点「发送测试消息」验证管理员自己已绑定的会话能收到（需先完成下面第 3 步）。

> 换域名、换 Token、点「重置 Webhook Secret」后都必须重新注册 Webhook，否则 Telegram 仍打旧地址或旧 Secret。

## 3. 用户绑定

1. 用户在网页打开「个人设置 → Telegram 通知」。
2. 点「生成绑定码」，得到 8 位绑定码（10 分钟有效，同一用户只保留最新一个）。
3. 在 Telegram 里向机器人发送 `/bind 绑定码`（或点页面上的深链自动带上 `/start 绑定码`）。
4. 绑定成功后回到网页点「刷新状态」。一个账号最多绑定 3 个会话，一个会话只能绑一个账号。

每个会话可独立设置：

- **通知开关**：关闭后不再推送，但保留绑定。
- **推送范围**：全部邮件 / 仅临时邮箱 / 仅长期邮箱。

只支持**私聊**。群组里发送命令会直接被拒绝，避免邮件内容泄漏给群成员。

## 4. 命令与交互

| 命令                                 | 说明                                                                                            |
| ------------------------------------ | ----------------------------------------------------------------------------------------------- |
| `/start`                             | 查看绑定状态与菜单                                                                              |
| `/start <绑定码>` / `/bind <绑定码>` | 完成绑定（绑定码一次性）                                                                        |
| `/unbind`                            | 解除当前会话绑定（带二次确认按钮）                                                              |
| `/new [前缀]`                        | 创建临时邮箱；不填前缀则按「姓+名+生日」随机生成（如 liuxiang1998），沿用站点前缀规则与频率限制 |
| `/list`                              | 邮箱列表，按未读排序，可点进最近 5 封                                                           |
| `/id`                                | 查看当前会话 `chat_id`（排障用）                                                                |
| `/help`                              | 命令说明                                                                                        |

| 按钮           | 行为                                               |
| -------------- | -------------------------------------------------- |
| 查看正文       | 拉取纯文本正文（超长截断 3200 字），并自动标记已读 |
| 标记已读       | 只改状态，不改消息                                 |
| 在网页中打开   | 跳转 `/mail/<messageId>`                           |
| 删除该临时邮箱 | 二次确认后软删；长期邮箱不提供此按钮               |

推送正文包含：收件地址、发件人、主题、验证码（若识别到）、摘要（300 字内）、时间。

### 验证码提取

只做保守匹配，宁可漏报也不猜错：

1. 关键词上下文：`验证码 / 校验码 / 确认码 / 动态码 / 动态密码 / 登录密码 / 口令 / verification code / OTP / passcode` 后 16 字符内的 4–8 位数字；
2. 数字在前、关键词在后的反向写法；
3. 正文里独占一行的 6 位数字。

订单号、金额、年份这类数字不会被当成验证码。

## 5. 数据表

| 表                   | 作用                                                                      |
| -------------------- | ------------------------------------------------------------------------- |
| `telegram_bot`       | 单行配置：启用开关、Token 密文、Webhook Secret 密文、机器人信息、最近错误 |
| `telegram_link`      | 会话绑定：`chat_id` 唯一，按用户级开关与推送范围                          |
| `telegram_bind_code` | 一次性绑定码，10 分钟 TTL，`used_at` 原子消费                             |
| `telegram_update`    | `update_id` 去重表，Telegram 重推时直接丢弃                               |

`telegram_update` 保留 24 小时，绑定码保留 1 天后由 `sweep` 清理。

## 6. 安全设计

| 风险                | 处理                                                                                           |
| ------------------- | ---------------------------------------------------------------------------------------------- |
| Token / Secret 泄漏 | 只存 `encryptSecret()` 密文，接口只回末四位；日志不打印请求 URL（URL 里含 Token）              |
| Webhook 伪造        | 校验 `X-Telegram-Bot-Api-Secret-Token`，`safeEqual` 常量时间比较；未启用或未配 Secret 一律 404 |
| Secret 进访问日志   | 路径固定为 `/api/telegram/webhook`，Secret 只走请求头，避免 Nginx access log 落盘              |
| 重放 / 重推         | `update_id` 唯一索引去重，抢不到直接返回 200                                                   |
| 越权读信            | 所有查询都带 `userId`，回调只能操作绑定账号自己的邮箱与邮件                                    |
| 群组泄漏            | 只处理 `private` 会话                                                                          |
| 绑定码爆破          | 8 位、去混淆字符集、10 分钟有效、一次性消费，且必须已登录网页才能生成                          |
| 机器人被拉黑        | Telegram 返回 403 时自动把该会话 `notify_enabled` 置 0，避免持续重试                           |

## 7. 排障

| 现象                                         | 排查                                                                       |
| -------------------------------------------- | -------------------------------------------------------------------------- |
| 页面提示「管理员尚未启用」                   | `/admin/telegram` 打开启用开关并保存                                       |
| 注册 Webhook 报 `HTTPS url must be provided` | `siteUrl` 必须是公网 https 地址                                            |
| 注册成功但收不到更新                         | Nginx/CDN 是否放行 `POST /api/telegram/webhook`；确认没有缓存或 WAF 拦截   |
| Webhook 返回 401                             | Secret 不一致：后台「重置 Webhook Secret」后重新注册                       |
| Webhook 返回 404                             | Bot 未启用、Token 解密失败或数据库未迁移                                   |
| 收不到推送但绑定正常                         | 看 `/admin/telegram` 的「最近错误」；常见是用户拉黑机器人（403）或触发 429 |
| 推送延迟                                     | 推送在响应后异步发送，不阻塞收件回调；常看「最近错误」里的 429 与网络超时  |
| 命令没反应                                   | 是否在群组里发（不支持）；是否 Bot 被限制；`/id` 能否回复                  |

查看 Telegram 侧状态：

```bash
# 需要真实 Token，注意不要在共享终端里回显
curl -s "https://api.telegram.org/bot<TOKEN>/getWebhookInfo" | jq
```

`last_error_message` 与 `pending_update_count` 能直接说明问题。

## 8. 与收件链路的关系

```
Resend Webhook → processWebhook（验签/去重）→ ingestInbound（入库）
                                                   └→ notifyInboundMessage（best-effort）
```

- 通知在 `db.batch` 成功、计数更新之后触发，且**不 await**：不会拖慢 Resend 回调，也不会因为失败让 Resend 收到 5xx。
- 推送依赖常驻 Node 进程在响应后继续执行；若部署到会在响应后冻结的 serverless 平台，需要改成队列。
- 一封邮件命中多个本站地址时，仍只投第一个邮箱，推送也只针对该邮箱。
- 临时邮箱在考察期内收到首封邮件时，先完成「永久保留」的更新，再推送，因此推送里的有效期文案不会误导。

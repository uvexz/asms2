## 2. 已验证的链路

这些是本地真跑过的，不是写完代码就算数：

- 注册 → `BOOTSTRAP_ADMIN_EMAIL` 对应账号在无管理员时自动提权。
- 创建长期/临时邮箱 → 列表正确；临时邮箱初始 `expiresAt = createdAt + 3600s`。
- 模拟收件 → 入库、`<script>` 被净化、临时邮箱 `retainedAt` 有值且 `expiresAt` 清空。
- 失效的临时邮箱再收到信 → 进 `unrouted_message(expired)`，不复活。
- 用假 Key 调真实 Resend → 接口 502、错误信息透出、**配额回滚为 0**。
- API Key → `GET /api/v1/mailboxes` 200。
- `sweep` 无密钥 401，带 `CRON_SECRET` 返回统计。
- 关闭域名的「允许新建临时邮箱」→ 创建 temp 返回 400，创建 permanent 仍 201。
- Telegram：绑定码一次性消费、绑定/改推送范围/解绑正确；Webhook 无 Secret 401、坏 JSON 400、合法 update 200、重复 `update_id` 只落一条。

> 七家的真实收发还没联调过——手上没有七套 Key 和域名。目前验证的是适配器契约和错误映射，真实链路只有 Resend 用假 Key 打过一次（见上）。上线前按 [resend](./providers/resend.md) / [unitpost](./providers/unitpost.md) / [ahasend](./providers/ahasend.md) / [groundmail](./providers/groundmail.md) / [mailtrap](./providers/mailtrap.md) / [plunk](./providers/plunk.md) / [reloop](./providers/reloop.md) 各走一遍闭环，别跳。

## 4. 已知风险与运维注意

带「Resend」字样的两条是它特有的，其它服务商的坑写在各自接入文档里：

| 风险                          | 影响                             | 对策                                                                           |
| ----------------------------- | -------------------------------- | ------------------------------------------------------------------------------ |
| Resend Webhook 是团队级       | 同团队其他应用事件也会打进来     | 按收件域过滤，非本站 `ignored`                                                 |
| 无法 SMTP 退信                | 陌生地址发信只能丢弃             | 墓碑表可查；文案如实说明                                                       |
| 临时域信誉                    | 易被滥用注册,投诉会打挂域名      | 长期域与临时域分离;投诉 5 次/7 天自动关闭域名发件;新账号发件冷却               |
| Resend 速率约 2 req/s         | 并发发件 429                     | 429/408 返回 provider_retryable,用同一幂等键重试                               |
| 套餐域名/日发量限制           | 超额 403/429                     | 上线前核对套餐；后台观察错误                                                   |
| Turso 网络延迟                | 列表变慢                         | 冗余 `userId`、覆盖索引、`batch` 写入、列表不查正文                            |
| 远程事务限制                  | 多表写入一致性                   | 只用 `batch`；计数类允许最终一致                                               |
| 动态 OAuth 需重建实例         | 多实例生效有延迟                 | 版本号 + 30s 轮询                                                              |
| 邮件 HTML XSS                 | 账号被劫持                       | 净化 + sandbox iframe + CSP，三缺一不可                                        |
| 临时邮件堆积                  | 库膨胀                           | grace 后清正文、墓碑定期回收                                                   |
| Mailtrap / Plunk 验签无时间戳 | 抓包重放（去重记录 30 天后清理） | Plunk 密钥头一旦泄露即可伪造来信：定期轮换端点密钥，优先选带时间戳签名的服务商 |
| 工作量证明不是验证码          | 愿意花 CPU 的脚本仍能注册        | 与按 IP 限流、新账号发信冷却叠加；被针对时再接 Turnstile 等第三方              |

## 6. 需求决策

早期悬着的问题都按推荐值定了，下面这些结论不用再讨论：

- 临时邮箱：考察期内收到首封就永久保留，只收不发（站点开关可以放开）。
- 长期邮箱：按用户总量算配额，删掉后地址冷却 30 天。
- 域名：一域一商，新建权限按域名、按类型各管各的。
- 权限：管理员默认读不到正文、不能代发，也不做邮箱共享。
- 实时性：列表 20 秒轮询，暂时不上 SSE。
- 前端：只做中文，写信纯文本按空行转段落。
- Telegram：Webhook 接入（固定路径 + Secret 请求头）、绑定码 10 分钟一次性、只支持私聊、推送 best-effort。允许在 TG 里删临时邮箱，长期邮箱和邮件不删。

## 7. 2026-11-21 安全审计修复

按审计报告逐项修复，需要发布时执行一次 `db:migrate`（0012）和 `scripts/purge-orphans.ts`：

- **管理员引导提权**：只按 `BOOTSTRAP_ADMIN_EMAIL` 精确匹配；开启邮箱验证时须验证完成后提权。此前任意首个注册者都会被提权。
- **邮箱验证服务端强制**：新增 `requireVerifiedUser()`，收发 server fn、API Key、Telegram 机器人统一拦截；开启验证时不再把存量密码账号批量标记为已验证。
- **发信扇出**：`to + cc + bcc` 去重后合计 ≤20，cc/bcc 也校验格式；附件校验 base64、文件名与类型；发件 HTML 入库前同样净化。
- **API Key**：插件统一配置 120 次/分钟（原默认每天 10 次），前端创建不再传 server-only 字段；绑定单邮箱的 Key 只能看到该邮箱、不能新建邮箱。
- **Telegram**：封禁 / 未验证账号只允许解绑，推送停止；内部错误不再回显给用户。
- **收件路由**：停用邮箱、关闭收件的域名、非域名绑定服务商推来的邮件都进 `unrouted_message`；非法时间戳退回当前时间。
- **清理任务**：删邮件显式删除正文与附件（不依赖外键级联）；回收站按 `trashed_at`（移入时间）过期。
- **Webhook**：停在 `received` 超过 5 分钟的事件允许重投重跑；投递状态只单向推进；Mailtrap 兜底去重键加入请求体哈希；未知服务商类型直接报错。
- **服务商配置**：API 基地址须为公网 https（开发态放宽），修改地址必须同时重填 Key。
- **其它**：全站安全响应头、登录/注册/找回密码按 IP 限流、生产不再信任 localhost 来源、搜索 `LIKE` 转义通配符。

## 8. 2026-11-21 防滥用补充（迁移 0013）

- **人机校验**：自托管工作量证明（协议同 ALTCHA），保护注册、密码登录、找回密码、重发验证邮件；不依赖第三方服务，不需要放行外部脚本。站点设置可关，难度用 `POW_MAX_NUMBER` 调。

- 顺手修复：后台「站点地址」保存不生效（前端漏传 `siteUrl`）。

## 9. 2026-11-22 审计问题修复

- **发信幂等**:新增 `outbound_request`,发送请求先落库;同一幂等键的并发请求只允许一个进入服务商派发。超时/5xx/网络错误进入 `uncertain`,429/408 退款并进入可同键重试的失败态。API 支持 `GET /api/v1/send` 查询状态。
